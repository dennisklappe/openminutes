# Contributing

OpenMinutes is AGPL-3.0. By contributing you agree your work is released under the same licence.

## Setup

Requirements: Node 22, pnpm 9, Docker (for the compose stack and the bot image).

```bash
pnpm install
pnpm build
pnpm test
```

Run `docker compose up -d` for the full stack, see [Getting started](docs/getting-started.md). Copy `.env.example` to `.env` first. The Python whisper service in `services/whisper` has its own tests (`pytest`).

## Before opening a PR

`pnpm format:check`, `pnpm lint`, `pnpm typecheck` and `pnpm test` must pass; CI runs the same.

## Conventions

- Strict TypeScript, small focused modules, no dead code. Comments only for a non-obvious why.
- Docs are short and scannable: a lead, tables, callouts (`> [!NOTE]`), `<details>` for deep detail and Mermaid diagrams (plain ` ```mermaid ` blocks, no colours or `init`, 5 to 12 nodes). `pnpm docs:check` parses every diagram.
- Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`). Work on a branch and open a PR against `main`; PRs are squash-merged, so the PR title is the commit message.
- Platform selectors (Meet, Teams) live in one module per platform with tests against recorded fixtures.
- No telemetry, ever. Never include real meeting content, personal data or secrets in code, fixtures, screenshots or issues.

## Adding a provider

Providers are one file each in `packages/providers/src/transcription` or `packages/providers/src/summary`.

1. Copy the closest existing provider (`groq.ts` is a good template for an OpenAI-compatible Whisper API).
2. Define a zod `configSchema` with `.meta()` for the label, help text and options. Settings renders the form from it.
3. Export the provider with `defineTranscriptionProvider` or `defineSummaryProvider`.
4. Add it to the list in `packages/providers/src/registry.ts`.
5. Add tests in `packages/providers/test` using the fake `fetch` from `helpers.ts`. Tests never call a real API.
6. Add a row to the table in [docs/providers.md](docs/providers.md).

## Platform fixtures

Each platform has one selectors module in `packages/platforms/src` with a version string, and fixtures in `packages/platforms/fixtures/<platform>`. Unit tests parse the fixtures, so a platform change shows up as a failing parse.

To refresh one:

1. Join a test meeting with a dedicated account. Never record a real customer meeting.
2. In DevTools, copy the outer HTML of the broken part (participant grid, chat panel or prejoin), with one speaking and one silent state.
3. Anonymise names, emails and images. Keep class names, `jsname` and `data-*` exactly as served.
4. Replace the fixture, update the selectors and bump the version constant.
5. Run `pnpm --filter @openminutes/platforms test`, then `pnpm test`.
6. Open a PR titled `fix(platforms): <platform> <part> selectors` with the date you recorded it.

The live test procedure is in [docs/maintainers.md](docs/maintainers.md).

## Releases

- [release-please](https://github.com/googleapis/release-please) cuts releases from Conventional Commit titles: `feat` bumps the minor, `fix` the patch, `!` or `BREAKING CHANGE:` the major (the minor below 1.0). Merging its release PR tags `vX.Y.Z` and publishes the multi-arch images to GHCR. Publishing is off until `PUBLISH_IMAGES` is `true`, see [docs/maintainers.md](docs/maintainers.md).
- A new migration is a new file in `packages/db/drizzle` generated by drizzle-kit. Migrations only go forward. Never edit one that has shipped.
- `e2e/upgrade.sh` upgrades a running stack between two images and checks the data survives. Run it when you touch migrations, the Dockerfile or compose.
- `e2e/transcripts/run.sh` scores speaker attribution and word error rate with synthetic meetings. Run it when you touch `packages/core/src/speak*` or `services/whisper` (downloads about 400 MB).
